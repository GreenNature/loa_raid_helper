# 인식 기술 선정과 학습 도입 기준

초기 구현은 **정규화 ROI + OpenCV 템플릿 비교 + HP 숫자 전용 OCR**을 사용함. 고정 위치의 작은 UI를 읽기 위해 전 화면 객체 탐지 모델을 학습하는 비용을 먼저 지불할 필요가 없음. 실제 게임 화면의 정확도는 아직 측정하지 않았으며 보정·평가 자료를 확보해야 함.

| 목표 | 초기 기술 | 선정 이유와 한계 |
| --- | --- | --- |
| HP 줄 수 | 좁은 한 줄 ROI + RapidOCR 문자 인식 모델 | 이미 위치가 정해져 있어 문자 검출 모델을 생략함. 줄 수 표기 외 문자열과 낮은 신뢰도는 거부함 |
| 버프·스킬 아이콘 | 회색조 `matchTemplate` + 제한적 배율 후보 | 고정 UI와 등록한 아이콘 종류에서 학습 데이터 없이 동작함. 쿨다운·겹침·애니메이션 상태는 별도 검증이 필요함 |
| 대기실 클래스 | 대기실 ROI의 아이콘 템플릿 + 수동 시너지 매핑 | 직업별 문구를 데이터로 관리함. 같은 클래스의 인원과 슬롯은 계산하지 않음 |
| 레이드·보스 여부 | 레이드 앵커 + 보스 앵커, 대기실 앵커 분리 | HP 숫자만 보였다는 이유로 보스로 간주하지 않음. 여러 앵커가 모순되면 `unknown`을 반환함 |
| 기믹 안내 | 신뢰도·연속 관측·HP 임계값 통과 | 한 프레임의 숫자 오류와 중복 안내를 줄임. 실제 공략과 전투 속도 검증이 필요함 |

## HP 문자 인식

`NumericOCR`는 `rapidocr-onnxruntime`에 포함된 문자 인식 모델을 CPU에서 지연 로드함. 문자 검출과 각도 분류는 사용하지 않음. 첫 번째로 레이드·보스가 함께 확인된 프레임에서만 모델을 불러오며 ONNX Runtime 스레드를 제한함. 설치 패키지의 모델을 사용하므로 실행 시 별도 모델 다운로드를 요구하지 않음.

기본 모델의 한글 보스명 인식은 보장하지 않음. 현재 보스는 이름 OCR 대신 사용자가 등록한 `boss_anchor.id`로 식별함. HP 문자열은 최대 세 자리 숫자, 선택적 `x/X/×`, 선택적 `줄` 형태의 전체 문자열만 허용함. 숫자만 일부 추출하여 다른 UI 숫자를 HP로 재해석하지 않음. OCR 신뢰도 기준 미달, 허용 범위 밖, 해석 불가능한 문자열은 HP를 `None`으로 유지함.

HP ROI에는 줄 수 한 줄만 포함해야 함. 현재 숫자 전처리는 단색 HUD 배경을 가정하고 Otsu 이진화로 밝거나 어두운 소수 전경의 경계를 찾은 뒤 4픽셀 여백을 붙임. 숫자의 자리 수와 ROI 여백 변화에 대응하기 위한 초기 처리이며 HP 바·보스명·다른 텍스트가 포함되면 경계가 잘못 잡힐 수 있음. 실제 글꼴과 효과가 겹친 화면의 검증은 아직 필요함.

글자가 작거나 테두리가 강한 실제 캡처에서 오인식하면 ROI 크기, 게임 UI 배율, 전처리 후보를 같은 검증 세트로 비교함. 실측으로 필요한 처리만 선택하거나 `FrameAnalyzer(config, ocr=...)` 어댑터를 교체함. 한글 보스명 기능을 추가하려면 한국어 모델·문자사전·출처·해시를 별도로 검증해야 함.

## 아이콘과 앵커

템플릿은 회색조 정규화 상관계수로 비교하고 `0.75, 0.9, 1.0, 1.1, 1.25, 1.5` 배율 후보의 최고 점수를 사용함. 기본 임계값은 0.88임. 회색조 비교는 밝기 차이에 어느 정도 대응하지만 색상만 다른 아이콘을 구분하지 못할 수 있음. 점수는 분류 확률이 아니므로 임계값 0.88을 정확도 88%로 읽으면 안 됨.

단색·저분산 템플릿을 거부하고 작은 ROI에서만 아이콘을 찾음. 레이드 앵커는 전체 프레임, 보스 앵커는 상단 `boss_roi`, 대기실 앵커와 클래스는 `lobby_roi`, 버프는 `buffs_roi`에서 비교함. 레이드·보스 앵커와 대기실 앵커가 동시에 나타나면 단계가 모순되므로 `unknown` 처리함. 현재 템플릿별 최상 일치만 확인하므로 같은 아이콘의 여러 위치와 인원 수는 반환하지 않음.

일치 임계값은 양성·음성 화면 양쪽으로 보정함. 아이콘 강조·쿨다운 음영·중첩 숫자·UI 배율별 변화를 따로 기록함. 템플릿 매칭만으로 “스킬 사용 가능”을 판단하려면 사용 가능·쿨다운 상태의 시각적 차이를 평가해야 함. 초기 구현은 등록한 모양의 존재를 표시하며 스킬과 버프의 논리 조합이나 지속 시간을 추론하지 않음.

## 단순 영상처리와 AI 도입 순서

1. UI 위치가 고정되고 무늬가 충분히 구분되면 ROI·템플릿 방식으로 시작함.
2. 색상으로 상태가 분명히 나뉘는 경우 HSV 색상 마스크, 활성 영역 비율, 쿨다운 음영 비율 같은 영상처리 후보를 검토함. 동일 화면에서 기준값을 정하고 검증함.
3. ROI 위치는 안정적이지만 아이콘 상태가 다양한 경우 잘라낸 아이콘의 작은 분류 모델을 검토함. `활성/비활성/알 수 없음` 클래스와 오분류 비용을 먼저 정의함.
4. 위치가 이동하거나 겹침 때문에 ROI가 안정적이지 않을 때 객체 탐지를 검토함. 박스와 클래스 라벨이 필요하며 추론 시간·CPU 배포 크기까지 비교함.

실제 실패 화면이 충분히 쌓였고 단순 보정으로 해결되지 않을 때 다음 단계로 진행함. 인식률, 오안내 빈도, HP 완전 일치, 최초 지연·평균 지연의 목표를 기능별로 정해야 함. 실제 게임 데이터 없이 학습 모델을 추가하는 것은 정확도 근거가 되지 않음. 현재는 학습 프레임워크와 사용자 게임 모델을 설치하거나 학습하지 않았음.

## 데이터 수집·라벨링 흐름

먼저 [보정 도구](calibration.md)로 관심 영역과 템플릿을 저장함. PNG와 manifest에는 ID, 용도, 출처, 해시, ROI를 기록함. 원본은 개인 로컬 경로에 두고 공유가 필요한 샘플만 선택함.

분류 모델을 검토할 때는 잘라낸 이미지를 `class_name/`별로 나누고 원본 캡처 묶음 ID, 해상도, UI 배율, 게임 상태를 기록함. 객체 탐지를 검토할 때는 CVAT 또는 Label Studio 같은 도구에서 아이콘 박스와 클래스를 지정하고 COCO 등의 표준 형식으로 내보낼 수 있음. 해당 외부 라벨링·학습 도구는 초기 필수 환경에 포함되지 않음.

연속 프레임을 무작위로 흩어 놓으면 거의 같은 이미지가 학습·검증에 섞일 수 있음. 캡처 세션·해상도·배율 묶음 단위로 학습/검증/테스트를 분리함. 비슷한 아이콘, UI 없음, 로딩, 오버레이, 가림, 낮은 밝기 등 음성 샘플을 함께 수집함. HP는 이미지별 숫자 정답과 읽으면 안 되는 화면의 `null`을 라벨링함.

고정 테스트 세트에서 `tools/evaluate.py`로 기준선 결과를 남긴 뒤 새로운 모델 어댑터를 같은 자료로 비교함. 도입하는 모델의 버전, 학습 데이터 범위, SHA-256, 라이선스, 전처리, CPU 추론 시간을 기록함. PyInstaller에 포함할 ONNX 모델과 사전은 오프라인 실행으로 다시 확인함. 새 학습 도구와 문서는 실제로 모델 도입이 결정될 때 선택한 프레임워크와 데이터 스키마에 맞춰 추가해야 함.
